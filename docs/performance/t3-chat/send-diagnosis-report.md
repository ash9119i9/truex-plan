The user's clarification is decisive: both first and follow-up questions appear immediately, then the answer waits. Current send handlers already make the optimistic user setter before any creation/network await. Therefore moving the optimistic row cannot explain the observed answer delay. The backend has separate preparation overhead before `turn/start`, and runtime/provider first-output wait after it; these must be measured separately.

## Actual path and uncovered waiting

1. `frontend/app/page.tsx:1532–1567`: validate, set local lock and creating/sending state, clear owned draft, append pending user, then `ensureSession`, then `transport.send`. The lock ends at response acceptance in `1597–1601`, not agent completion. Editor remains usable; another submission is guarded until acceptance.
2. First message only: `prepareSession` (`1463–1478`) awaits session creation. `ensureSession` (`1519–1525`) confirms mode only if older-platform creation failed to reflect the chosen mode. Configured creation has already removed that normal extra hop. Sidebar refreshes at `1476`, `1529`, `1569` are fire-and-forget, not awaited gates, though concurrent resource contention remains a separate measurement question.
3. `PlatformService.message` (`platform/src/service.ts:1492–1523`) awaits authorized session read, complete configuration and `/resume`, then inserts pending message, optionally saves first title, then `/turns`. Accepted duplicates still perform configuration/resume before discovering the receipt (`1505–1513`).
4. `configuration` (`410–496`) serially reads agent, model, attached tenant MCPs, attached owner MCPs, reserved tenant names when owner MCPs exist, DNS-validates each connector, and finally skills. MCP URL revalidation protects against DNS rebinding and must remain (`platform/src/mcp.ts:253–295`). Each failed DNS lookup can currently wait up to 5 seconds (`227–245`), so multiple troubled connectors create a realistic serial delay. This is a conditional failure bound, not evidence that the user's DNS is slow.
5. `resume` (`service.ts:1451–1479`) awaits runtime resume, approval confirmation, optional saved-plan check, unconditional settings replay for any saved settings, status/fingerprint persistence. Nonempty plan causes an extra session read even if unchanged (`1676–1685`).
6. Warm `ThreadManager.resume` (`agent-core/src/manager.ts:545–550`) skips underlying `thread/resume` when fingerprint is unchanged, but returns **full** `snapshot(id)`. Window/source optimizations for history and SSE do not change this POST response: `snapshot` defaults to all retained message/thinking bodies (`760–807`). Sending only needs operational/configuration acknowledgment; transcript serialization remains unnecessary on this path.
7. `ThreadManager.message` (`667–717`) serializes per thread, applies pending config if needed, starts the timing clock at `691–699`, then sends `turn/start`. Cold load performs `thread/resume` then `thread/goal/get` (`585–627`), so cold/resident and changed/unchanged config must be distinguished. Runtime `CodexClient.request` ensures app-server startup (`client.ts:230–232`); an already initialized client uses the fast path (`104–112`).
8. On gateway routes only, `model-gateway/src/server.ts:134–185` reads/caches profile, parses input and invokes the adapter; chat adapter `adapters/chat.ts:297–332` awaits provider fetch then streams. Responses profiles route directly (`platform/src/service.ts:429–443`), bypassing gateway. No frontend tweak removes upstream model computation or tool time.

`platformRoundTripMs` starts only immediately before `/turns` (`service.ts:1521–1534`). It excludes session read, configuration, DNS, resume, plan/title writes and settings replay. `acceptMs` and `ttftMs` start later still, in Manager.message, and completed-turn metrics are finalized in `manager.ts:1379–1399`. Neither tells us full input-to-acceptance or input-to-first-visible-answer time. `ttftMs` clocks the first `item/agentMessage/delta` (`manager.ts:1628–1655`), excluding earlier reasoning events and downstream SSE/React paint. Gateway `ttfbMs` is first emitted response frame (`responses.ts:41–55`, `logging.ts:82–85`), not universally first output-text delta. Gateway request ID may also differ from platform's because gateway receives runtime model calls; end-to-end correlation needs explicit validation.

## Focused ordered fix plan

1. **Measure complete phases on actual first and follow-up send before optimizing the seconds.** Add optional safe Server-Timing/service phase measurements for authorized session, configuration (DB and DNS separately), resume response build/bytes, settings, persistence, runtime acceptance. Browser marks submit, optimistic paint, receipt, first reasoning, first answer text and paint. Record runtime resident/cold and config changed/unchanged. Reuse existing turn timing rather than redefining it. Gateway routes need profile lookup, provider headers, first provider chunk, first emitted text/tool/reasoning and retry-count correlation; direct routes require equivalent runtime transport evidence. Never log prompts, configuration bodies, tokens or credentials. Acceptance: sum boundaries consistently and distinguish server latency from stream/main-thread rendering.
2. **Remove transcript payload from send preparation, retaining authoritative guards.** Add explicit lean resume/prepare response using existing `operationalSnapshot` content + exact approval/config acknowledgment; keep normal resume/history contracts default-compatible. Continue cold loading, tenant enforcement, changed-config reload and pending changes. Measure response bytes and first-output delay for long conversations; tests must preserve saved plan, approvals, goals and restart/source recovery. Do not replace resume with a skip based on stale browser knowledge.
3. **Reduce configuration's serial waits without retaining stale privileges.** After authorized session/agent lookup, run independent model, tenant MCP, owner MCP and skill reads concurrently; conditional reserved-name lookup can start with owner MCP result. Validate/decrypt using deterministic existing order; run bounded DNS validation, preferably deduplicated per hostname per build. Retain revalidation, tenant-name precedence, allowlists, encryption, fail-closed model/skill policy and current DNS-outage semantics. Measure paired injected DB/DNS and actual remote phase results. Avoid adding broad caches until scope, invalidation and security ownership are explicit.
4. **Apply saved settings once per acknowledged runtime configuration version, not every warm send.** Current `mcpFingerprint` describes MCP config only, so blindly dropping `/capabilities` would leave warm model/effort changes unapplied. Carry version/digest or actual applied-state acknowledgment inside the lean preparation boundary and atomically apply under Manager's existing per-thread lock. Test changed settings, restart, overlapping update/send, running steer and failed acknowledgment. This removes a measured hop where settings are present.
5. **Optimize measured runtime/upstream first-output only after step 1 identifies it.** Check connector startup/tool discovery, reasoning effort, model/provider service tier, context size and any retries. Compare the same owned prompt/configuration/route in a synthetic or user-approved probe; keep answer-quality and permissions criteria. A 35ms turn acceptance and multi-second delta gap cannot justify generic frontend rendering changes or an invented provider speed claim. Do not add automatic retry of message creation or turn start.
6. **Small resilience cleanup when the path is touched:** after ownership validation, accepted duplicate receipt can return before config/resume; retain database uniqueness for concurrent new claims and existing unknown/pending outcomes. This avoids unnecessary work and prevents a previously accepted receipt being obscured by current connector/model outage. Verify conflict/same-client payload semantics before promising retries. First-create plus turn atomic bootstrap remains deferred: existing configured creation already removed a hop, while a new protocol requires durable identity and uncertain-result recovery.

T3 comparison supports immediate optimistic dispatch (`ChatView.tsx:9347–9382`), one turn command with draft bootstrap configuration (`9446–9524`), and releasing its send guard after command result (`9672`). Truex already matches the immediate-row and acceptance-bound lock behavior. T3's `ProviderSessionManager` separately owns live session residency (`66–71`, `384–390`); adopting that architecture wholesale would exceed the measured need. T3 still opens a provider session and starts a turn (`ProviderTurnStartService.ts:522–526`, `1166`), so no claim of zero provider startup wait or T3 latency equivalence is justified.

No fix was implemented or deployed. Risks left to verify: long-history resume response cost, live Mongo round trips, actual configured connector startup/DNS, gateway/direct-route provider wait and browser first-answer paint. Existing tenant/approval safety, per-thread serialization, message uniqueness and unknown-receipt handling must survive any optimization.
