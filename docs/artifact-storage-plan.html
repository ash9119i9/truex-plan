Truex Artifact Storage

Move every file a conversation touches (uploads, generated documents, visualizations, exports) from agent-core's pod disk into S3, with metadata in each tenant's Mongo database, and build the attach, preview, library and share features on top. Agent skills move to S3 too, so a skill can carry its industry specs and reference files, not just a SKILL.md.

30 Sep 2026Branch feat/design-v2Covers backlog: document attaching, document preview, document enrichment, conversation export, Knowledge, Share, SAP push bridge, skills implementation, configuring skills, AWS use case

Summary

Today files live in business-workspaces/<tenant>/<uuid>/files/ on a single agent-core pod's volume. They are capped at 1 MB, moved between services as base64 JSON, invisible to Mongo, and deleted together with the workspace. S3 becomes the durable copy. agent-core keeps its local folder as a cache so the agent's tools stay fast and unchanged. Platform owns metadata, permissions and short-lived signed URLs, so the browser uploads to and downloads from S3 directly.

Recommended decisions

  • One private bucket per environment, tenant-first key prefix, SSE-KMS, versioning on, public access blocked.
  • agent-core writes through to S3 behind an ArtifactStore interface (local | s3). Keys are built from the thread's tenant marker, never from model input.
  • New artifacts collection in each tenant DB. Platform learns about agent-created files from the existing records ingestion loop.
  • Browser uploads use a presigned POST with a size range. Downloads use a 302 to a 5-minute presigned GET, so existing <a href> links keep working after auth lands.
  • Flag-gated with ARTIFACT_STORE=local|s3, following the features.ts pattern. The old /documents routes stay as shims.
  • Skills become tenant-owned, immutable, versioned bundles under t/<tenantId>/skills/ in the same bucket, created by uploading a zip or writing in an in-app editor. The skill document in Mongo holds the S3 location, and the agent's skills list references skills by id. At thread start, platform resolves them and agent-core fetches, caches and injects them into the thread config, alongside MCP.

UX details that matter

  • Upload states: queued, uploading (percent), scanning, ready, failed with a reason such as "Too large, max 25 MB" or "File type .exe isn't supported". Send waits until all pills are ready.
  • The existing auto-prompt "Read the uploaded document and summarize" becomes optional. Attachments ride on the message, so the user writes their own ask.
  • Revisions reuse the existing sourceId chain. The card shows "v3" and a version menu. Old versions stay downloadable.
  • Deleting a file removes it from the list at once, with an Undo toast. The bytes are hard-deleted after 30 days.
  • If S3 is unreachable, generated files still work from the local cache, and the card shows "Saving…" until the sync catches up.

Architecture

Each service keeps the job it already has. agent-core produces and reads bytes, platform owns who may see what, and the browser talks to S3 only through URLs that platform signs.

flowchart LR
  B[Browser] -- "1 request upload" --> P[Platform]
  P -- "presigned POST" --> B
  B -- "2 upload bytes" --> S[(S3 bucket)]
  B -- "3 complete" --> P
  P -- "import artifactId" --> A[agent-core]
  A -- "GetObject to cache" --> S
  A -- "tool writes: local + PutObject" --> S
  A -- "artifact record" --> P
  P -- "metadata" --> M[(Tenant Mongo: artifacts)]
  B -- "download" --> P
  P -- "302 presigned GET" --> B

agent-core

  • Add an ArtifactStore interface (put, get, head, delete, copy) with LocalStore (today's behavior) and S3Store. ConversationFiles.save writes locally first, then does a PutObject with a SHA-256 checksum. On failure it retries through a small on-disk outbox, so a tool call never fails because of S3.
  • read_conversation_file and export_workspace_file hydrate from S3 on a local miss. The pod folder becomes a cache the sweeper can evict safely, which removes the "workspace deleted = documents lost" problem.
  • Emit an artifact record (id, key, size, sha256, mediaType, sourceId, turnId, toolCallId) into the existing /threads/:id/records stream. Emit a matching SSE event so the chat can render a file card without polling.
  • New route POST /threads/:id/documents/import copies a browser-uploaded object into the conversation's cache and registers it with the agent.
  • Fork does a CopyObject into the new conversation's prefix, matching today's copy behavior.
  • Workspace work/ stays local scratch until Phase 7. Only exported or final deliverables go to S3.

Platform

  • artifactConfig(env) in features.ts style: ARTIFACT_STORE, ARTIFACTS_S3_BUCKET, AWS_REGION, ARTIFACT_MAX_UPLOAD_MB, ARTIFACT_URL_TTL_S. It is injected into PlatformService, with the non-secret parts exposed on /api/features.
  • Ingestion (service.ts:1119) upserts artifact records into the tenant DB, the same way it persists messages and traces.
  • Every artifact route checks the tenant, and once auth ships also the owner or chat visibility, before signing a URL.
  • Messages gain attachmentIds. Platform checks that each belongs to the session, then passes the file references to agent-core with the turn.

Frontend

  • lib/artifacts.ts: upload with XHR progress to the presigned POST, then complete, list, rename, delete. It keeps the api() error model and node:test coverage.
  • Composer: an attach chip in the chips slot, pending pills in above, and a drop and paste target on .composer.
  • FileCard in chat-messages.tsx, driven by message attachments and artifact events. The visualization token path stays as it is.
  • A Files tab in session-activity.tsx, the Knowledge page in the v2 side nav, and the Share dialog wired to the topbar button.

Agent skills from S3

Skills already work end to end. Today's path is: the agent's skillIds, then catalog truex_skills (body inline in Mongo), then platform skills() with the tenant allow-list, then the thread config's skills, then agent-core skillSet(), then skillInstructions() in the base instructions. This plan makes skills tenant-owned, stores every version in S3, and lets a skill carry reference files.

Decided

  • Skills belong to a tenant. They live in the tenant's own database and under the tenant's S3 prefix, like agents and MCP profiles. Other tenants can't see or attach them.
  • There are two ways to create a skill: upload a zip, or write it in a text editor in the app.
  • Agents use the latest version by default. An agent can pin a version when a spec must not change under it.

This replaces the earlier split where skills sat only in the shared catalog. Existing catalog skills keep working as a read-only "Truex library", still governed by allowedSkillIds. A tenant can copy a library skill into its own skills to edit it.

What users see

  • Skills page (next to Agents in the side nav). A list showing name, description, current version, "Used by N agents" and last updated. Each skill can be disabled.
  • New skill, then Write a skill. A form with three fields:
    • Name: a slug, checked as you type.
    • Description, labelled "When should the agent use this?"
    • Instructions: a Markdown text area with a Preview tab and a size counter against the 64 KB limit.
    Save publishes v1. Each later edit publishes a new version and keeps any reference files.
  • New skill, then Upload a zip. Drop a .zip with SKILL.md at the root and optional reference files. Before you click Publish, the page shows the parsed name, description and file list with sizes, plus a clear message for each problem, such as "SKILL.md is missing" or "specs/big.pdf is over 20 MB".
  • Skill detail.
    • Instructions and reference files, each file downloadable.
    • Version history with who published each version and when.
    • "Used by" agents.
    • Actions: Edit instructions, Upload new version, Download as zip.
  • Agent dialog. A skills picker listing the tenant's skills and allowed library skills. Each attached skill shows "Latest (v4)", or a pinned version picked from a dropdown.

Two shapes of skill

ShapeContentsHow the agent gets it
Instructions only (always the result of the editor)SKILL.md aloneThe body goes into the base instructions, exactly as today.
Skill with references (zip upload)SKILL.md plus files/: industry specs (PDF, DOCX, XLSX), Markdown, CSV and JSON code lists, templatesThe body goes into the instructions. Reference files are listed by name and size, and the agent reads them on demand with a skill-file tool. They are never inlined.

Bundle in S3

t/<tenantId>/skills/<skillId>/<version>/SKILL.md
t/<tenantId>/skills/<skillId>/<version>/files/<path>
t/<tenantId>/skills/<skillId>/<version>/text/<path>.txt      extracted at publish time (PDF, Office)
t/<tenantId>/skills/<skillId>/<version>/manifest.json      { sha256, files: [{ path, size, sha256, mediaType }] }
catalog/skills/<skillId>/<version>/...                      Truex library (today's catalog skills, migrated)

Versions are immutable. Publishing writes a new version prefix and never overwrites, so an agent pinned to v3 keeps getting v3. Skills have no lifecycle expiry. Deleting a tenant removes its skills along with the rest of t/<tenantId>/.

Where the key lives

// tenant DB: truex_skills (new, one per tenant; unique index on name)
{ _id: "skl_<uuid>", name, description, version, enabled,
  origin: "editor" | "upload" | "library-copy",
  storage: { prefix: "t/<tenantId>/skills/<id>/<version>/", sha256, size, fileCount },
  versions: [{ version, sha256, origin, publishedAt, publishedBy? }],
  createdAt, updatedAt }

// tenant DB: truex_agents
{ ..., skills: [{ skillId: "skl_…", version?: 3 }] }   // version absent = latest enabled
                                                       // skillIds (library) still read for existing agents

The S3 location sits on the skill document, and the agent stores a reference plus an optional version pin. Putting the raw S3 key on the agent would mean editing every agent whenever a skill is republished, and nothing would check that the key belongs to the agent's tenant.

Runtime flow

  1. On thread start or resume, platform's agent config (service.ts:392) resolves agent.skills from the tenant's truex_skills. Library skills still go through findSkills with the allow-list. Disabled or missing skills fail with SKILL_CONFIGURATION, as today. For each skill it reads SKILL.md and manifest.json from S3, cached in memory by sha256.
  2. Platform sends the thread config with skills: [{ name, description, version, body, sha256, prefix, files: [{ path, size, mediaType }] }]. This is the same payload that carries mcp_servers.*.
  3. agent-core skillSet() validates the new fields and checks that every prefix starts with t/<this thread's tenant>/skills/ or catalog/skills/. A bad config therefore can't point a thread at another tenant's bundle. The skills are saved in the thread marker, and skillInstructions() renders the body plus a short "Reference files" list for each skill.
  4. New agent-core dynamic tools list_skill_files and read_skill_file(skill, path, offset, limit) read from a content-addressed cache at <home>/skill-cache/<sha256>/. A cache miss triggers a download with a checksum check. The tools reuse the PDF and Office text extraction in file-tools.ts and page long files to protect context.
  5. Resume and fork re-read the marker. An agent on "latest" picks up a new version when platform rebuilds the config, which already happens on resume. A pinned agent never changes.

Skills can't go into the Codex config the way MCP does. MCP servers become Codex config keys, but Codex skill loading can't be limited to the skills a thread was given, which is why discovery is off today. Skills therefore keep entering through the base instructions plus our own tool, which needs no vendor/codex changes.

Publishing

  • Editor. POST /api/skills takes JSON { name, description, body }. Platform renders SKILL.md with front matter and writes it to a new version prefix. For an edit it also copies the previous version's files/ and text/ with CopyObject, so reference files carry over.
  • Zip. The browser uploads to a presigned POST at t/<tenantId>/uploads/<uploadId> (at most 50 MB). POST /api/skills/import then streams the zip with a pinned, maintained zip reader, validates it, extracts text, writes the version, and deletes the staging object. Uploading a zip for an existing skill creates its next version.
  • Validation:
    • SKILL.md is required, and its front matter name and description must match the existing rules. Body at most 64 KB.
    • Zip at most 50 MB, at most 200 MB uncompressed, at most 20 MB per file, at most 200 files, allowed types only.
    • No symlinks, absolute paths or .. (zip-slip). A high compression ratio is rejected as a zip bomb.
  • Publish order: write the files, extracted text and manifest to the new version prefix, then bump version in Mongo. A failed publish leaves the current version untouched, and the reconciler removes the orphaned prefix.
  • npm run skill -- publish|list|disable <tenant> ... stays available for ops and bulk loads.
  • Migration: each existing catalog skill is uploaded to catalog/skills/ as a SKILL.md-only library bundle at the same version. Agents' skillIds keep resolving without edits.

Guardrails

  • Skill text is instructions to the model. Once auth ships, only tenant admins create or edit skills. Until then, any user of the tenant can, the same as agent creation today (platform/src/index.ts:127). The existing fence() tag escaping stays, and reference files come back from the tool as data, not instructions.
  • agent-core gets read-only access to t/*/skills/* and catalog/skills/*, plus the prefix check above. Platform alone can write skill prefixes.
  • If S3 is down at thread start and the skill is already cached by sha256, the thread starts normally. Otherwise it fails with SKILL_CONFIGURATION. A failed read_skill_file returns a tool error and the chat continues.
  • Token budget: bodies keep today's limits (64 KB each, 256 KB per agent), and reference files are never inlined. A later option for agents with many skills sends descriptions only, with a load_skill tool (backlog: token efficiency).

Bucket and keys

s3://truex-artifacts-<env>-<region>/
  t/<tenantId>/s/<sessionId>/a/<artifactId>/<versionNo>   bytes (no user filename in the key)
  t/<tenantId>/s/<sessionId>/a/<artifactId>/<versionNo>.txt   extracted text for the agent
  t/<tenantId>/s/<sessionId>/a/<artifactId>/<versionNo>.pdf   rendered preview (Phase 4)
  t/<tenantId>/uploads/<uploadId>                         staging, expires after 1 day
  t/<tenantId>/exports/<exportId>                         conversation exports, expire after 7 days
  t/<tenantId>/skills/<skillId>/<version>/...            tenant skill bundles, immutable (see Agent skills)
  catalog/skills/<skillId>/<version>/...                  Truex library skills, read-only
  • The filename lives in Mongo and is applied through ResponseContentDisposition at signing time. Renames are metadata-only, and user text never reaches key paths.
  • The tenant-first prefix makes it cheap to delete a tenant, report usage, and write per-tenant IAM or STS session-tag conditions later.
  • Bucket settings: Block Public Access on, BucketOwnerEnforced, SSE-KMS with a bucket key, versioning on, a TLS-only bucket policy, and CORS restricted to FRONTEND_ORIGIN for POST and GET.

Data model

New collection artifacts in each tenant DB (truex_t_<id>). It extends the existing ConversationFile shape, so the current UI types keep working.

{
  _id: "art_<uuid>",
  sessionId, projectId?, ownerId?,            // ownerId filled once auth ships
  kind: "upload" | "generated" | "visualization" | "export",
  name, mediaType, size, sha256,
  rootId, version, sourceId?,                 // version chain (existing sourceId)
  storage: { key, versionId? },
  status: "pending" | "ready" | "failed" | "deleted",
  createdBy: "user" | "agent", turnId?, toolCallId?,
  text?: { key, chars }, preview?: { key, status },
  title?, description?, mode?,                // visualization fields kept
  createdAt, updatedAt, deletedAt?
}
indexes: {sessionId, createdAt}, {ownerId, createdAt}, {rootId, version},
         {status, deletedAt}, {kind, createdAt}

uploads   { _id, sessionId, ownerId?, key, name, maxBytes, expiresAt }   TTL index on expiresAt
tenants   + { storage: { quotaBytes, usedBytes, retentionDays, maxUploadMB, allowedTypes[] } }

The write order keeps Mongo and S3 consistent: create the row as pending, put the object, mark it ready. A reconciler job fails stale pending rows and removes unreferenced objects.

Security and tenancy

  • Key construction is server-only. Tenant and session in a key come from the thread marker (agent-core) or the resolved tenant context (platform). Model output and user filenames never shape a key.
  • Least-privilege IAM. agent-core's role gets Get, Put and Copy on t/*/s/*. Platform's role gets presign rights (Get, and Put through the POST policy) plus Delete. Neither role gets bucket-wide List. Both use IRSA or a task role, with no static keys in .env.
  • Signed URLs. GET URLs last 5 minutes and uploads 15 minutes. Uploads carry content-length-range and a fixed key. Responses use no-store and nosniff. HTML and SVG are always served as attachments, and visualizations keep rendering in the sandboxed iframe.
  • Content checks on upload complete. Check the extension allow-list, sniff magic bytes against the claimed type, and optionally scan with GuardDuty Malware Protection for S3 before ready.
  • Auth dependency. Until USER_SCOPED_MCP_PLAN lands, anyone who can reach platform can fetch any tenant file by id, same as every other /api route today. Phases 1 to 3 are fine for the internal team. Library, share and anything for outside users waits for auth, and ownerId plus chatVisibility enforcement is added then.
  • Audit. Turn on S3 server access logs or CloudTrail data events for the bucket. Platform logs every signed URL with request id, tenant and artifact.
  • Deletion. Member removal (already specified to delete that user's sessions) and scripts/tenant.mjs drop must also queue prefix deletes.

Lifecycle, quotas, cost

ObjectRule
Conversation filesStandard, then Intelligent-Tiering after 30 days. Kept until deleted or the tenant's retentionDays passes.
Deleted filesSoft delete in Mongo, object removed after 30 days. Noncurrent S3 versions expire after 30 days.
Upload stagingExpire after 1 day. Abort incomplete multipart uploads after 1 day.
ExportsExpire after 7 days (regenerate on demand).
Local cache on podsThe sweeper evicts files/ by LRU once the S3 copy is confirmed, so WORKSPACE_TTL_DAYS can finally be set safely.

Proposed limits: 25 MB per upload (a presigned POST allows more if needed), 500 MB per conversation, and a tenant quota set by admins. Agent context stays protected because the agent reads extracted text through the existing size-limited read_conversation_file.

Cost is small at this scale. S3 Standard is roughly $0.023 per GB-month in us-east-1, so 100 GB is a few dollars a month before requests and transfer. Please check current pricing for the chosen region. KMS requests are the one line to watch, which is why bucket keys are on.

Phased rollout

Each phase ships behind ARTIFACT_STORE=s3 and can be turned off without data loss, because the local copy is always written first.

  1. Foundations. Bucket, KMS and IAM (IaC, Terraform or CDK to be decided). ArtifactStore interface, MinIO service in deploy/compose.yaml for dev, artifactConfig, artifacts collection, and pinned @aws-sdk/client-s3, s3-presigned-post and s3-request-presigner on the same release as the existing Secrets Manager client. No user-visible change.
  2. Durable files and downloads. Write-through for all producers, artifact records into Mongo, 302 downloads, file cards in chat, Files tab. Fixes the 1 MB export mismatch. Backfill script uploads existing business-workspaces/*/*/files.
  3. Tenant skills from S3. Tenant truex_skills collection, S3 bundles, Skills page with the Write-a-skill editor and zip upload, skills picker with version pins in the agent dialog, platform resolution, agent-core skill cache with list_skill_files and read_skill_file, and migration of catalog skills to the library. Doesn't wait on auth, but the admin-only rule is added when auth lands. Backlog: "skills implementation", "Configuring their Skills".
  4. Attach in chat. Presigned POST, composer attach, drag and drop, paste, attachmentIds on messages, attachment chips on user messages. Backlog: "Document Attaching in the Chat".
  5. Preview. Images, PDF (pdf.js), Markdown, CSV and text. Office files first show extracted text, then a LibreOffice worker renders PDF previews. Backlog: "Document Preview", "Chat Rich Preview".
  6. Knowledge library. Cross-chat list, search, rename, delete with undo, versions, attach from library, project scoping. Needs auth for "mine". Backlog: v2 "Knowledge nav + page".
  7. Export, share, SAP bridge. Conversation export (md, pdf, docx through the existing document libraries), topbar Share, and push_workspace_file reading from the store once the SAP tool's name and arguments are known. Backlog: "conversation export", "Share button", "SAP push bridge".
  8. Admin and workspace durability. Usage and retention settings in the admin UI, quota enforcement, and snapshots of work/ on turn/completed so a lost pod or a second replica can resume a conversation. Backlog: "implementing the AWS usecase".

Testing

  • Unit tests: an in-memory ArtifactStore for agent-core and platform. Key builder tests confirm tenant and session can't be escaped (../, unicode, very long names).
  • Integration: add MinIO beside mongodb-memory-server in platform/test/http.test.ts. Cover upload, complete, message with attachment, the agent reading the file, download redirect, delete, and a cold-cache hydrate after wiping the local folder.
  • Failure cases: S3 down during a tool call (outbox drains later), expired upload URL, oversize upload rejected by the policy, type mismatch rejected at complete.
  • Frontend: node:test for lib/artifacts.ts (fetch and XHR mocked) and attachment state reducers. Manual browser pass on drag, drop, paste and preview until a DOM test setup exists.
  • Tenant isolation: tenant A can't list, sign or import tenant B's artifact ids.
  • Skills:
    • Editor save creates v1, and an edit creates v2 that keeps the reference files.
    • Zip import rejects a missing SKILL.md, zip-slip paths, zip bombs and oversized files.
    • A SKILL.md-only skill renders the same instructions as today's inline skill (snapshot test on skillInstructions).
    • read_skill_file pages a PDF spec.
    • A pinned version stays fixed after a republish, and a "latest" agent moves on resume.
    • A cache hit works with S3 down.
    • Tenant A can't list, attach or read tenant B's skills. agent-core rejects a config whose prefix belongs to another tenant.
    • A library skill outside the allow-list is rejected.
