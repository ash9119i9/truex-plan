Truex caching and optimization plan

Redis for shared state, an immutable document cache, a frontend response cache, and removal of repeated work across the platform, agent-core, model-gateway and frontend. Built from seven code audits. vendor/codex is not touched.

What the audits found

  • Opening a conversation is the slowest action. The browser makes four calls. On the server, three of them run a full sync from agent-core, and history() reads the same session five times. service.ts:1040-1118
  • The browser caches nothing. Reopening a conversation, switching a tab or opening a sheet refetches the data. The same MCP list is fetched by three components. lib/api.ts:98
  • Each streamed token re-renders the whole page. page.tsx has 57 state hooks, and every past message's Markdown is re-parsed on each token. page.tsx:443, chat-messages.tsx:379
  • Every stream reconnect resends a full snapshot, even when replay succeeded. The snapshot is also built twice. manager.ts:1062-1086
  • No compression, no pagination and missing indexes. Sending one message loads the whole history. The sessions list does an in-memory sort. service.ts:689, 1216
  • Both platform replicas poll every session every 2s. This doubles the load on agent-core and lets both replicas persist the same records before either acknowledges them. service.ts:1119-1155
  • Anthropic reports zero cached input tokens on every turn, even though cache control is set. backlog.txt:58
  • Documents never change after they're written (a new UUID each time, no overwrite), yet they're served no-store as base64 JSON. file-tools.ts:285

Ground rules

Redis speeds things up; it never holds the only copyMongo and agent-core stay the source of truth. If Redis is lost or evicts keys, things get slower but never incorrect.
Redis is optionalIf REDIS_URL isn't set, services use in-process caches, which keeps local dev as it is today.
Every key includes the tenantAuthorization runs before any cache read. HTTP caching is always private.
Each layer has its own flagEvery layer can be turned on and off separately, following the features.ts on() pattern.
Measure firstServer-Timing headers and client-side timing marks go in before any cache, so each phase shows a before and after.
Sensitive data is never cachedTurn context (the masked prompt) stays no-store in every layer.

Frontend response cache

NEXT_PUBLIC_CLIENT_CACHEbiggest improvement users will see
  • Add a stale-while-revalidate layer in lib/api.ts: show the cached copy immediately and refresh it in the background. Key it by tenant and URL, share in-flight requests, clear it on writes, and send If-None-Match when the server sets ETags.
  • Cache these for the whole page load: models, capabilities, schemas and features.
  • Share one MCP list per agent across the three components that use it, and invalidate it when mcpVersion changes.
  • Keep an in-memory LRU of the last 20 conversations (detail, traces, timings) so a reopened conversation shows immediately. The stream then fills in anything new.
  • Show agents, sessions and projects from a localStorage copy on boot, which removes the "Loading agents…" wait. Clear it on tenant switch and, once auth exists, on logout.
  • Keep goal history, model context and the documents list when switching tabs or reopening sheets. Remove the 400ms goal-tab delay.

Redis setup and coordination

REDIS_URLcompose + k8s
  • Add a Redis service to deploy/compose.yaml and deploy/kubernetes.yaml, and pass REDIS_URL to the platform (lines 62-76) and the gateway (lines 132-135).
  • Add a shared module in shared/ exposing getJSON / setJSON / lease / publish / subscribe. It needs a command timeout of about 50ms, a circuit breaker that falls back to in-memory, and metrics for hits, misses and errors.
  • Use a poller lease so only one replica polls at a time: SET lease:poll:{tenant} NX PX 5000. If Redis is unavailable, both replicas poll as they do today.
  • Invalidate caches across replicas over pub/sub (channel truex:inv). Wire it to the gateway's unused clear(), extended with per-id eviction, and to the tenant registry. Key rotation and profile disable then take effect everywhere at once.
  • Record the last persisted cursor per session for stream-triggered writes, so extra tabs and replicas stop repeating goal and plan writes. index.ts:537-600
  • Use Redis SET NX as a fast pre-check for idempotency on command() and on setting titles. The Phase 0 Mongo unique index stays as the guarantee.
3

Server-side caches backed by Redis

SERVER_CACHE
  • Catalog (models, skills): keep it in an in-process L1 cache backed by Redis. The key includes catalog:ver, which scripts/tenant.mjs, demo.mjs and the migration scripts increment. Use a 60s TTL as a safety net for writes made directly to Mongo.
  • Tenant config (agents, MCP lists, allow-lists): the key includes cfg:{tenant}:ver, which the three write endpoints increment, publishing to truex:inv at the same time.
  • Inputs for configuration() (agent + model + MCP + skills) come from those caches, which takes 4+N Mongo reads off every message send.
  • ETags on /models, /agents, /agents/:id/mcp, /capabilities and /sessions, built from the version stamp. Responses use Cache-Control: private, no-cache plus Vary on the tenant header.
  • Cache the active-tenant list for the poller, so it stops querying the registry twice every tick.
  • Cache completed traces, helper-agent transcripts and goal history under an immutable key. Anything still running or growing is not cached.
4

Document and visualization cache

DOCUMENT_CACHEaligns with S3 plan

Documents and visualizations are never overwritten: a revision gets a new id with sourceId. That makes (tenant, sessionId, fileId) a safe permanent key. Caching works in tiers, from nearest to the user to the source:

Browserprivate, max-age=31536000, immutable on content, plus an in-memory memo for visualization JSON
Platform RedisBytes ≤ 1 MB and visualization HTML, cached for 24h. Repeat views skip agent-core.
agent-core diskThe source today. Once the S3 plan ships, it becomes an LRU cache in front of S3.
S3 (later)302 redirect to a presigned GET. The sha256 becomes the content address.
  • Compute sha256 in save() and store it in the metadata. Use it for a strong ETag, and it matches the S3 plan's checksum.
  • Serve binary from agent-core as a stream with the right Content-Type, replacing base64 JSON. This removes the 33% size overhead and the 2 MB body limit problem once uploads grow to 25 MB.
  • The document list gets an ETag built from the file count and newest createdAt. When a file is saved, a stream event marks the list as stale, so the UI stops refetching on every sheet open and on every change to timings.length.
  • HTML and SVG are always downloaded as attachments, with nosniff kept. Visualizations keep rendering in the sandboxed iframe.
  • Authorization (tenant plus session ownership) always runs before a cached copy is served.
Check first: the audit found no delete or rename endpoint for files, but that wasn't fully confirmed. If one exists or is planned, it needs to remove the Redis key and switch that route off immutable. A browser can also keep a cached file after the workspace cleanup job deletes the conversation. That's acceptable for private caching, but you should approve it.

Decisions needed

  1. Redis flavour and host. ElastiCache for Valkey or Redis OSS on AWS, with valkey/valkey or redis in compose for dev. The Node client would be ioredis at a pinned version.
  2. Frontend cache. Build a small cache ourselves (roughly 150 lines, no new dependency), or adopt TanStack Query at a pinned version.
  3. Keeping lists in localStorage before auth exists. Agents, sessions and projects would stay readable on a shared machine until login and logout exist.
  4. Browser caching documents for a year, even after the cleanup job deletes the workspace.
  5. Order of phases. The proposal is 0 → 1 → 2 → 3 → 4, with 5 and 6 running in parallel once Phase 0 measurements are in.
Sources: seven read-only code audits of the frontend, platform, agent-core, model-gateway, deploy config, the document path, and a broad optimization sweep. Line references reflect the working tree on 30 Sep 2026. Nothing has been measured yet, which is why Phase 0 starts with measurement.
