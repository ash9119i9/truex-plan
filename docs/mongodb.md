# MongoDB configuration

The application reads configuration and never inserts default agents, model profiles or skills on startup. The MCP settings panel can create MCP profiles and update agent attachments. `.env` contains connection/service settings, not model credentials.

## Database layout

Data is split between one shared **catalog** database and one database per **tenant**.

| Database                         | Env var            | Collections                                                                       |
| -------------------------------- | ------------------ | --------------------------------------------------------------------------------- |
| Catalog (e.g. `truex_catalog`)   | `CATALOG_MONGO_DB` | `truex_models`, `truex_skills`, `tenants`                                         |
| Default tenant (e.g. `truex`)    | `MONGO_DB`         | `truex_agents`, `truex_mcp`, `sessions`, `messages`, `projects`, `traces`         |
| Any other tenant `<id>`          | generated          | the same collections as the default tenant                                        |

- Unset `CATALOG_MONGO_DB` means the catalog is `MONGO_DB`. That is the pre-tenancy layout (everything in one database), and it keeps working unchanged.
- The default tenant (id `default`) always uses `MONGO_DB`, so existing agents, MCP profiles and conversations stay where they are.
- Every other tenant uses `truex_t_<id>` with `-` replaced by `_` (tenant `acme-corp` → `truex_t_acme_corp`). The name is generated by the server and never taken from request input.
- Models and skills are shared through the catalog; agents and MCP profiles belong to one tenant. An agent may reference catalog models and skills, and MCP attachments (`truex_mcp.agentIds`) must stay in the agent's tenant database.
- The model gateway reads `truex_models` from `CATALOG_MONGO_DB` (falling back to `MONGO_DB`). Gateway tokens may carry the tenant id, used only for usage logs.
- Agent-core keeps per-tenant workspaces under `business-workspaces/<tenantId>/`.

Indexes are ensured on startup. Catalog: `tenants {dbName: 1}` (unique) and `truex_skills {name: 1}` (unique). Each tenant database: `messages {sessionId: 1, at: 1}`, `sessions {status: 1}`, `sessions {projectId: 1, createdAt: -1}` and `traces {sessionId: 1, startedAt: 1}`.

## Agent — `truex_agents` (tenant database)

Agents created through the app are saved with `scope: "general"`. Existing records without a scope still use the runtime's `"business"` default; set their scope to `"general"` and start a new conversation to apply it.

Example in mongosh notation; IDs below are illustrative, not existing records.

```js
{
  _id: ObjectId("000000000000000000000001"),
  name: "My assistant",
  description: "Your description",
  systemPrompt: "Your instructions",
  persona: "You are Nova, a writing companion.",
  scope: "general",
  modelProfileId: "000000000000000000000002",
  skillIds: ["000000000000000000000004"],
  sandbox: "read-only",
  approvalPolicy: "never",
  enabled: true
}
```

`modelProfileId` and skill references may be strings or ObjectIds and point into the catalog database. MCP attachments live on each profile as `agentIds: [String(agent._id)]`; `agent.mcpProfileIds` is a legacy field retained after migration and does not attach tools. `description`, `systemPrompt`, `sandbox`, `approvalPolicy`, `mcpProfileIds` and `skillIds` may be omitted. Defaults are an empty description, generic helpful-assistant instructions, read-only sandbox, never approvals, no MCP servers and no skills. `persona` replaces the default Truex identity line, and `scope: "general"` lifts the business-only framing so the agent helps with any request. Both are optional; omitted means the Truex identity and `scope: "business"`. Platform guardrails (connector policy, data handling, no host access) apply to every agent and are not configurable. `enabled: false` hides an agent. Unknown application-specific fields are preserved and ignored; for example, `browserUseCloud` does not itself configure a browser integration.

## Model — `truex_models` (catalog database)

```js
{
  _id: ObjectId("000000000000000000000002"),
  provider: "Your provider",
  modelName: "your-model-id",
  baseUrl: "https://provider.example/v1",
  apiKey: "<provider credential stored only in this document>",
  wireApi: "responses",
  reasoningEffort: "medium",
  enabled: true
}
```

The existing lowercase `apikey` spelling also works. Use one spelling consistently; if both exist, `apiKey` takes precedence. Missing `wireApi` means `responses`. This Codex revision explicitly removed Chat Completions support: declaring `wireApi: "chat"` is a configuration error, and changing the string alone will not make a chat-only endpoint implement Responses. Choose a provider/model that supports the Responses API. `reasoningEffort` is optional; `serviceTier: "auto"` is omitted from runtime overrides. Disabled models are unavailable for sessions, and so are models outside the tenant's allow-list.

## Skill — `truex_skills` (catalog database)

```js
{
  _id: ObjectId("000000000000000000000004"),
  name: "quarterly-summary",
  description: "Summarize a quarter of sales data into a one-page brief.",
  body: "# Quarterly summary\n\nSteps the agent follows...",
  version: 3,
  enabled: true
}
```

`name` must match `/^[a-z0-9][a-z0-9-]{0,63}$/` and is unique (enforced by an index). `body` is the SKILL.md Markdown body; `description` tells the model when the skill applies. Bump `version` whenever `body` changes. Agents opt in through `skillIds`. Disabled skills and skills outside the tenant's allow-list are not loaded.

## Tenant — `tenants` (catalog database)

```js
{
  _id: "acme-corp",
  name: "Acme Corp",
  dbName: "truex_t_acme_corp",
  status: "active",
  allowedModelIds: ["000000000000000000000002"],
  allowedSkillIds: ["000000000000000000000004"],
  createdAt: "2026-09-29T10:00:00.000Z",
  updatedAt: "2026-09-29T10:00:00.000Z"
}
```

`_id` must match `/^[a-z0-9][a-z0-9-]{0,31}$/`. `dbName` is unique and server-generated; for `default` it is `MONGO_DB`. `status: "disabled"` rejects the tenant's requests (`TENANT_DISABLED`); unregistered ids other than `default` are rejected (`TENANT_NOT_FOUND`). The default tenant works without a registry entry; the migration and `npm run tenant` register it when needed.

**Allow-lists.** When `allowedModelIds` or `allowedSkillIds` is present, the tenant's agents may only use those catalog entries (matched by `_id`, stored as strings). A missing field means every enabled entry is allowed; an empty array allows none. Manage them with `allow-models` / `allow-skills` rather than by hand.

## MCP — `truex_mcp` (tenant database)

```js
{
  _id: ObjectId("000000000000000000000003"),
  name: "my-mcp",
  scope: "tenant",
  agentIds: ["assistant"],
  transport: "http",
  url: "https://mcp.example/mcp",
  apiKey: "<MCP credential stored only in this document>",
  auth: {kind: "header", headerName: "x-api-key"},
  capabilities: {connectTimeoutMs: 30000, requestTimeoutMs: 120000},
  enabled: true
}
```

For bearer authentication use `auth: {kind: "bearer"}`. For no authentication use `auth: {kind: "none"}`. HTTP credentials are translated into runtime `http_headers`; timeout milliseconds become seconds. A stdio profile uses `transport: "stdio"`, `command`, optional `args` and `env`. A profile may alternatively contain a raw runtime `config` object.

Enabled tenant profiles with the agent's ID in `agentIds` load for every conversation using that agent. User profiles also require `scope: "user"` and an `ownerId` matching the conversation owner. The platform never loads unscoped profiles. `autoConnect` and capability-discovery flags do not control attachment or authorization.

For databases using `agent.mcpProfileIds`, run the existing scope migration described in [MCP deployment and recovery](MCP_AGENTCORE_FIX.md). The platform returns `MCP_MIGRATION_REQUIRED` for enabled, unscoped profiles referenced through that legacy field instead of silently creating a chat without them. Migrated profiles may retain the old references; detachment still uses only `agentIds`.

## Configure MCP from the chat UI

Select an agent and open **Connected tools**. Create an HTTP connector using no authentication, a bearer token, or an API-key header, select it, and save the attachments. Local command connectors are blocked. Tenant admins can manage tenant connectors; user connectors belong to their creator. Credentials saved through the API are encrypted using the platform's MCP encryption key and never returned by the API.

The platform rereads configuration on conversation creation and before new turns. It applies attachment and credential changes on resume, or queues them until an active turn completes. Tool schemas are discovered by the runtime and tool calls/results use the existing chat cards.

- `GET /api/agents/:id/mcp` returns credential-free profiles and attachment IDs for the caller, plus tenant profiles. Tenant admins can also manage tenant attachments through this form.
- `POST /api/mcp` creates a user HTTP profile owned by the authenticated caller.
- `POST /api/agents/:id/mcp` with `{ "profileIds": ["..."] }` sets the caller's attachments. An empty array detaches their servers. User saves do not remove tenant attachments or another user's attachments.
- Tenant admin routes under `/api/tenant/mcp` and `/api/agents/:id/tenant-mcp` manage shared tenant connectors.

These routes enforce tenant, ownership, and role checks. Raw runtime `config` overrides remain database-managed. Keys are decrypted only when building the runtime payload.

## Operational data

These collections live in each tenant database (`truex` for the default tenant). `sessions` stores routing, status, audit and timing metadata; `messages` stores user messages and authoritative assistant finals. `traces` stores one observability trace per turn (`_id` `${sessionId}:${turnId}`, index `{ sessionId: 1, startedAt: 1 }`): step timings, token usage, rate limits and masked privacy findings. It never holds prompt text; the masked "what the model saw" view is served live from agent-core and is not persisted. The application does not reuse or migrate existing `truex_runs` or `truex_conversations` schemas.

## Tenant commands

`npm run tenant` (`scripts/tenant.mjs`) manages the registry. It reads `MONGO_URI`, `MONGO_DB` and `CATALOG_MONGO_DB` from the environment, then `platform/.env`.

```sh
npm run tenant -- create acme-corp Acme Corp            # register + create truex_t_acme_corp indexes; no-op if it exists
npm run tenant -- list
npm run tenant -- disable acme-corp                     # or: enable acme-corp
npm run tenant -- allow-models acme-corp <modelId...>   # --all removes the restriction
npm run tenant -- allow-skills acme-corp <skillId...>   # --all removes the restriction
npm run tenant -- drop acme-corp --confirm acme-corp
```

`allow-models` / `allow-skills` reject ids that are not in the catalog. `drop` requires the id to be repeated, prints the registry entry, the database and each collection with its document count, then deletes both. It refuses `default` and any database that is not the generated `truex_t_` name. There is no undo; back up first.

## Migrating to the catalog layout

An existing single-database deployment keeps working with `CATALOG_MONGO_DB` unset. To split the catalog out:

1. **Dry run:** `CATALOG_MONGO_DB=truex_catalog npm run migrate:tenancy -- --dry-run` prints what would be copied and writes nothing.
2. **Run:** `CATALOG_MONGO_DB=truex_catalog npm run migrate:tenancy`. It copies every `truex_models` document (and `truex_skills`, if any) from `MONGO_DB` into the catalog, inserting only missing `_id`s and never overwriting existing ones. `_id` types (string or ObjectId) are preserved, so agent `modelProfileId` references still resolve. It registers the `default` tenant with `dbName: MONGO_DB`, ensures the catalog indexes and prints a summary. It deletes nothing and is safe to run again.
3. **Verify:** set `CATALOG_MONGO_DB` on **both** the platform and the model gateway, restart them, and check that models appear in the UI, an existing chat still resolves its model, and `npm run tenant -- list` shows `default`.
4. **Optional cleanup,** once verified: drop the old copies by hand in mongosh (`use truex; db.truex_models.drop()`, and `db.truex_skills.drop()` if present). The migration never does this; until you do, edits to the old collections are silently ignored.

The script exits with an error when `CATALOG_MONGO_DB` is unset or equals `MONGO_DB`: there is nothing to migrate.

## Tenant selection (development only)

**Authentication is not implemented yet.** Until it is, the platform picks the tenant with a development resolver, and any client that can reach the API acts as that tenant:

- `DEV_TENANT_ID` (default `default`): the tenant every request uses.
- `DEV_TENANT_HEADER=on`: lets the `X-Truex-Tenant` request header choose the tenant. Any caller can then switch tenants, so use it only locally.
- With `NODE_ENV=production` the platform refuses to start with this resolver unless `ALLOW_DEV_TENANT=on`. Setting that is an explicit acknowledgement that clients are not isolated from each other's tenants.

Tenant separation is currently a data-layout boundary, not a security boundary. Keep the platform on an internal network, as with the rest of the unauthenticated development API.

## Credentials

Public agent summaries project out both credential spellings. No API exposes raw model/MCP documents. Diagnostic events and advanced capability responses pass through credential redaction. Do not commit real sample documents containing credentials; `a.json` is ignored locally for that reason.
