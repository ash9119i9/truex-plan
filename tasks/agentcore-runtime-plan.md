## Overview

Run `runtime-adapter` inside an AWS Bedrock AgentCore microVM, one session per chat, and let `platform-next` reach it through `InvokeAgentRuntime` instead of plain HTTP. Local HTTP and AgentCore call the same adapter operations; only the transport differs. Legacy (`platform/`, `agent-core/`, root `Dockerfile`) is untouched.

```text
platform-next RuntimeClient.send()
  ├─ HTTP transport (today)      → runtime-adapter :4400
  └─ AgentCore transport (new)   → InvokeAgentRuntime(sessionId = f(tenantId, chatId))
                                      → bridge :8080 /invocations
                                          → allowlist + session check + adapter token
                                          → runtime-adapter 127.0.0.1:4400 (same process)
```

## Architecture decisions

- **Bridge and adapter in one Node process.** The bridge calls `createAdapterServer` (`runtime-adapter/src/server.ts:51`) on loopback instead of spawning a child, so there is no child-crash handling to port from legacy.
- **Adapter starts on the first invocation**, not at boot, because `/mnt/state` is mounted only from then (legacy behavior).
- **Per-boot adapter token**, generated by the bridge and added to forwarded requests. IAM authenticates the caller; `RUNTIME_ADAPTER_TOKEN` is not in the AgentCore environment.
- **Envelope:** request `{method, path, query, body, bodyBase64}`. Event streams and successful file reads pass through raw; everything else, errors included, returns HTTP 200 with `{status, body}` so adapter codes (`CHAT_BUSY`, `SKILLS_MISSING`) survive AWS's 424 rewrite.
- **Session ID derived, not stored:** `chat-` + sha256(`tenantId/chatId`) hex (69 chars, AWS minimum 33). No schema change; recovery works for chats whose session was never recorded. The function is duplicated in both packages with one shared test vector.
- **One chat per session:** the bridge recomputes the session ID from the request's chat and rejects mismatches and a second chat in the same session.
- **`/ping`** reports `HealthyBusy` while adapter `activeRuns > 0`, else `Healthy`; it never sets `time_of_last_update` on every ping (that blocks idle timeout).
- **Single SDK attempt** (`maxAttempts: 1`, no socket timeout). Throttling, `RetryableConflictException` and network errors map to `AdapterUnreachable`, which the run executor already handles by reattaching, not resending.
- **Not ported from legacy:** record spool/acks, `window`/`sync` read options, multi-owner routing, Mongo-stored session IDs.

## Risks and mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Session-ID header name (`X-Amzn-Bedrock-AgentCore-Runtime-Session-Id`) unconfirmed | High: session binding bypassable or broken | Confirm in AWS docs during Task 3; bridge fails closed if header missing |
| AWS 424 rewrite hides adapter errors | Medium | `{status, body}` envelope for all non-stream responses (Task 2) |
| Streams cut at 60 min | Medium | Executor reconnects with `after=<seq>`; covered in Task 9 |
| Cold starts on recovery sweep / file copy | Medium: cost, latency | Existing 190 s first-response wait; measure in slice 12 |
| Chats started locally show `THREAD_LOST` after switching to ARN | Low in dev, High in prod | Start prod clean, or record runtime per chat (open question) |
| Uploads need coding, which is off on AgentCore | Medium: feature gap | Documented; enabled only after sandbox check (`tasks/coding-agent-plan.md`) |
| Prebuilt `.runtime/agentcore/codex` artifact not present locally | Low | Task 4 builds it via root `Dockerfile --target codex-artifact` |
